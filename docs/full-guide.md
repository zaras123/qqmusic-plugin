### 账号操作

账号操作**仅主人可用**，会真实修改主人账号数据；命令只按主人自己的账号槽位执行，
不会被「一律走主人账号」换到别的槽位。每条命令末尾必须带 `确认` 或 `confirm`，否则只回用法、不执行。
完整命令可在群里发 `#qqm账号操作` 查看。

```text
#qqm歌单新建 我的歌单 确认
#qqm歌单删除 123 确认
#qqm歌单加歌 123 456:1 789:1 确认
#qqm歌单删歌 123 456:1 确认

#qqm喜欢歌曲 123:1 确认
#qqm取消喜欢 123:1 确认
#qqm收藏歌单 7011,7012 确认
#qqm收藏歌单取消 7011 确认
#qqm收藏专辑 9001,9002 确认
#qqm收藏专辑取消 9001 确认

#qqm不喜欢 歌曲 123 确认
#qqm取消不喜欢 歌手 888 确认
#qqm清空不喜欢 确认

#qqm发评论 歌曲 123 好听 确认
#qqm删评论 cm_123 确认

#qqm音响力点赞 10001 确认
#qqm音响力取消点赞 10001 确认
#qqm音响力隐私 1 确认

#qqm私信发送 10001 1 你好 确认
#qqm私信删除会话 s_1 确认
#qqm私信删除消息 s_1 m_1 确认
#qqm私信清空会话 s_1 确认
#qqm私信设置 1 open 确认
#qqm私信全部已读 enc_1 确认
#qqm私信卡片操作 10001 1 m_1 确认
```

`歌曲ID:类型` 中，类型省略时默认为 `1`；多个歌曲、歌单或专辑 ID 可用英文逗号分隔。
音响力隐私 `1` 表示隐藏、`0` 表示公开。写接口成功后如果上游仍在 `data.code` 返回非零业务码，
插件会显示失败原因，不会误报成功。

### 听歌时长统计

`#qqm听歌` 看自己、`#qqm听歌榜 [今日|本周|总]` 看本群排行。数字来自**本机器人真正发出去的歌**
（`#qqm听N` / `#qqm播放` / 卡片解析 / 定时点歌 / 随机推荐 —— 凡是走发歌那条路的都算），
所以它表示的是"这群人真的点播了多少"。

- **只记账，不上报**：不扫码、不调任何平台接口、也不向任何平台发任何东西 —— 与平台账号和风控无关。
  平台时长任务见下方「平台时长任务」，是否计入以平台返回统计为准。
- **时长怎么算**：按歌曲时长累计（`interval`，拿不到才解析 `duration`）；单曲按 1 小时封顶。
  时长拿不到的曲目只计**次数**，不编一个数字出来。
- **连续天数**：今天还没听**不算断连**（从昨天往回数），所以每天早上的数字不会归零。
- **隐私**：群聊记在群账本、私聊记在个人账本，两类不混；只在群里能看群榜。
- **落盘**：Karin 运行目录 `@karinjs/karin-plugin-qqmusic/data/qqmusic-store.json` 之外的独立文件 `@karinjs/karin-plugin-qqmusic/data/qqmusic-stats.json`（插件包内 `.gitignore` 也豁免 `data/`，
  `#qqm强制更新` 的 `git clean` 豁免清单含 `data/`，强制更新不会冲掉）。写盘是**合并写**：
  5 秒内的多次点歌并成一次，群里连点几首不会触发几次全量序列化。
- **怎么调**：Karin WebUI →「① 基础设置 → 听歌时长统计 / 统计保留天数 / 统计人数上限」。
  配置键 `statsEnable`（默认开）、`statsKeepDays`（默认 60 天）、`statsMaxUsersPerGroup`（默认 100 人）。
  保留天数只裁剪**日粒度**（今日/近 7 天/连续天数用到的部分），累计时长不受影响；
  人数超限时先丢**最久没点歌**的那个人，活跃的人不会被顶掉。
- **单测**：`npm run test:stats`（纯本地，不需要 Karin / 不需要 API）。

### 平台时长任务

仅主人操作；需要更新到提供 `/listening/*` 的 API。两套框架使用相同命令：

| 命令 | 说明 |
|---|---|
| `#qqm刷歌 QQ 10 晴天 确认` | QQ 新增 10 分钟目标；歌名走 QQ 官方搜索，也可直接填 songmid |
| `#qqm刷歌 酷狗 10 确认` | 酷狗新增 10 分钟目标，需本人酷狗登录态 |
| `#qqm刷歌状态` | 当前任务；可加 QQ、酷狗或任务ID |
| `#qqm刷歌记录` | 当前账号最近五条任务 |
| `#qqm刷歌刷新 QQ` | 只核对已结束任务的延迟统计，不重放旧批次 |
| `#qqm刷歌停止 QQ 确认` | 停止该平台当前任务；也可指定任务ID |
| `#qqm刷歌统计 酷狗` | QQ 为今日时长，酷狗为累计时长 |
| `#qqm刷歌计划 QQ 歌手 周杰伦 60 一直 00:05 确认` | 每天 00:05 起补到 24 小时；可选单曲、专辑或歌手，每轮可轮换 |
| `#qqm刷歌计划 QQ 专辑 叶惠美 60 20次 00:05 确认` | 固定总轮数，不无限执行 |
| `#qqm刷歌计划列表` | 查看状态、轮次与生效时间 |
| `#qqm刷歌计划暂停 listen_xxx 确认` | 也支持继续、立即、删除 |
| `#qqm刷歌帮助` | 帮助卡片；无渲染器时返回完整文本 |

只使用发送者自己的账号槽，不受“一律走主人账号”的播放配置影响。启动、停止均须在命令末尾写「确认」。默认只读取 API 已保存的状态，机器人不创建定时轮询或重复提交任务。同一消息生成稳定请求标识；并发启动请求会被阻止。在途请求停止后可能仍被平台处理，应先查询状态。

`#qqm刷歌状态` 在 classic、apple、nebula、multi 四套主题中均有专用卡片，并显示当前歌曲名、歌手、任务状态、请求量、平台接收量和统计增量。请求时长、平台已接收量与查询确认的增量分别展示。后台不播放音频；酷狗不返回具体歌曲记录，专辑/歌手轮换仅适用于 QQ。增量可能包含其他客户端播放，**真实 QQ / 酷狗账号入账仍未完成验收**。普通帮助和完整帮助卡片中的相关条目也仅主人可见。

### 勋章进度（只读）

`#qqm勋章`（也收 `#qqm勋章任务` / `#qqm成就进度`）查的是**平台侧**的数据：平台记的听歌时长
明细 + 勋章活动任务进度。走 API 的 `/cgi` 透传两个只读方法：

- `music.listening.ListeningSvr.QueryListeningDetail` —— 听歌时长明细
- `music.activeCenter.ActTaskNewSvr.GetTaskList` —— 活动任务列表（要 `medalActID`）
- `music.activeCenter.PlaypagetaskSvr.GetTaskDetail` —— 播放页任务（没配活动 ID 时的**只读兜底**）

**勋章查询只读**：只把平台记录的进度读回来。平台时长任务使用下方独立命令，不会自动签到或领取奖励。

- **按本人账号查**：这几个方法匿名调用都回 `code=1000`，所以本人的 QQ 音乐账号得先登录
  （`#qqm登录`）；真没登录时命令只回一句「需要登录」，绝不编数字。登录正常也可能被上游
  拒绝：2026-10-18 线上实测 `QueryListeningDetail` 在登录态下回 `code=10007`，那是
  **本次时长查询被上游拒绝**，不是"没登录" —— 卡片会照实写「登录态正常 · 上游拒绝」，
  然后照常把能读到的播放页任务列出来。
- **按请求者本人查**：勋章进度不会套用「一律走主人账号」；谁发 `#qqm勋章`，就读谁的
  QQ 音乐账号进度，避免群里所有人都看到主人的数据。
- **活动 ID**：勋章任务按平台**当期活动**查，ID 会随活动轮换。填 Karin WebUI →「勋章活动 ID」
  （配置键 `medalActID`），留空就只查听歌时长。拿法是进 QQ 音乐 App 的勋章活动页，
  从请求里抓 `actID` —— 这是活动参数，不是账号凭据，不涉密。
  没填 `medalActID` 时会用**播放页任务**兜底：不需要活动 ID，直接读平台当前播放页的任务；
  真拿到数据才多补一段「播放页任务（补充，只读）」，配了活动 ID 就以活动任务为准、不掺这一路。
- **字段名还没钉死**：上游返回的字段名在插件侧**没有固化**（登录态下还没抓到样本）。
  所以解析是「已知候选名优先 + 其余标量原样列出」：真换了字段名，命令不会变空白，而是把
  平台返回的东西照实摆出来。拿到真实样本后再把名字收紧。
- **怎么调**：Karin WebUI →「① 基础设置 → 勋章进度（只读）/ 勋章活动 ID」。
  配置键 `medalEnable`（默认开）、`medalActID`（默认空）。
- **单测**：`npm run test:medal`（纯本地，不需要 Karin / 不需要 API / 不打网络）。

### 音质选项

`128` / `m4a` / `320` / `flac` / `ape` / `hires` / `atmos` / `master` / `atmos_master`

默认 `auto`：自动匹配歌曲最高可用音质，支持逐级降级。

> 📌 **关于「主人账号」**：默认每个群友点歌都用自己的登录态（`userKey` = 各自 QQ 号），没登录就是免登录状态、只能播免费曲。
> 「一律走主人账号」**默认开启**：主人账号**自动取最近一次扫码登录的账号**（无需手填），所有人点歌都按它取播放链 ——
> 全群都能播 VIP 曲，群友在共用同一 API 的自己机器人上登录过非 VIP 号也不影响。
> 机器人还没扫码登录过时开关等于没开（日志会提示一次）；`#qqm设置` 会显示当前生效的账号，标红说明该账号未登录。
>
> 只影响「播歌 / 取数据」；登录状态、取 CK、刷新这些仍只认请求者本人（否则会把别人的登录态误报成本人的）。访客 Token 也无法指定主人账号。
>
> 多账号想固定用某一个时，才在 `@karinjs/karin-plugin-qqmusic/config/qqmusic.yaml` 里手动填 `publicAccount`（留空=自动）。
> 不需要全员共用主人号时，在 Karin WebUI 关闭「一律走主人账号」即可。

> 📌 **关于其它平台凭据**：QQ 音乐之外的平台各有**独立**通道（哪家能配、怎么配，以帮助卡的音源行为准）：
> - **能扫码的**（`#qqm<平台>登录`）：QQ 音乐 App · 网易云 · 酷狗 · 汽水。
> - **只能粘贴 cookie 的**（`#qqm<平台>ck`）：**酷我**（没有扫码通道）；网易云 / 酷狗 / 汽水（扫码被风控掐时的备用路）。
> - **Apple Music** 是特例：`#qqmamck` 收的是一份 **Netscape cookies 文件全文**（必须含 `music.apple.com` 那几行）。
> - **免登录的**（B站 / 咪咕 / Audius / JioSaavn）不用配；**YouTube** 卡的是出网代理（`YOUTUBE_PROXY`），配 cookie 没用。
>
> 粘贴 cookie 的命令**必须私聊**：凭据按人存（写进发命令那个人的槽位），群里发等于把账号借给全群 —— 机器人会直接拒收。
> 自己配的这份想全站共用 → 开「一律走主人账号」（Karin WebUI ① 基础设置）；`#qqm<平台>清ck` 只清自己那份，共享的与别人的都不动。
> 也可以在**Karin WebUI → 平台**里逐平台粘贴，与私聊发命令等效。

> 📌 **关于高音质（FLAC 以上）**：`hires` / `atmos` / `master` / `atmos_master` 是 **QQ 音乐绿钻会员限定**，且部分歌曲未上架这些音质。若显式设置了高音质却被降级，点歌卡片会直接标明原因（如「API 未返回链接（通常需绿钻会员）」，即账号非会员；「该歌曲未提供此音质」，即歌曲本身没出该档）。日志中 `音质选定: flac ... [hires:no-url, flac:ok]` 也可定位。

> 📌 **关于试听 / 海报 / 订阅 / 定时点歌**：
> - **副歌片段怎么选**：没有音频分析，用的是「40% 进度起」的启发式（流行歌副歌大多在那之后）；时长拿不到时用 ffprobe/ffmpeg 探一次，再不行从 60s 起放。片段固定 **128k 重编成紧凑 mp3**（`previewSec` 可调 10-60 秒）—— 试听只为判断好不好听，无损片段没有意义。
> - **歌词海报选句**：与试听同一副歌窗口（LRC 时间戳定位，兼容 QRC 字级标签，自动滤掉作词/作曲元数据行），四套主题都有独立的海报模板。
> - **订阅 / 定时是群级数据**（存在 `@karinjs/karin-plugin-qqmusic/data/qqmusic-store.json`，按群隔离）：插件包内 `data/` 已豁免 `#qqm强制更新` 的 git clean，不会把订阅冲掉；添加/删除限**主人**（整群推送的事），查看对全员开放。
> - **订阅推送**以「歌手歌曲列表出现增量」为准（与 `#qqm歌手` 同一份热门列表）—— 新歌爬进列表就会被推到群里，并写入本群点歌会话，收到推送直接 `#qqm听1` 就能播。bot 被移出群 / 发送连续失败时该订阅自动停用。
> - **定时点歌**到点后走与 `#qqm播放` 完全同一条发送链（详情卡 → 语音 → 群文件），「一律走主人账号」照常生效；机器人恰好在整点宕机时，**晚到 10 分钟内**照样补发。

### 演出票务命令


> **Karin 认插件的两条路**：`plugins/` 下的 git / 目录插件；以及**根目录 `package.json` 的依赖里带
> `karin` 字段的 npm 包**（node-karin 的 `collectNpmPlugins` 就是按这个扫的，`pnpm add` 会自动把它写进
> dependencies，所以方式 A 不用再做别的）。两条路都以 `package.json` 的 `main`（`dist/index.js`）为入口，

### 3.5 卡片字体（**Linux 容器必看**）

卡片上的中文优先用**宿主机装的字体**渲染。**2026-09-24 起插件自带一份 CJK 兜底字体**
（Noto Sans SC 子集，GBK 全集 21791 字，woff2 共约 13.7MB，SIL OFL 1.1 可随包分发）——
所以"容器里一个中文字体都没有"**不会再变成方块**：系统里没有中文字体时才会下载这份兜底字体。

不过它只是**兜底**：想要 2.0 主题设计稿那套观感（MiSans / PingFang），还是建议在宿主机装字体。

> **2026-09-25 补了三处漏网的** —— 都是同一类"裸机上悄悄画不出来"：字体早就随包发了，
> 但没接到每一张卡上。
>
> | 漏的地方 | 现象 | 现在 |
> |---|---|---|
> | `classic`（1.x 默认皮肤）压根没引自带字体 | 用 classic 时中文全是方块 | 11 个模板**逐个**都引了 `fonts/qqm-cjk.css` —— 每张卡都是独立 HTML 文档，漏一个那张就方块 |
> | 等宽字体栈（`--mono` / `ui-monospace`）没带 CJK | `#qqm点歌` 这类命令示例方块 | 四套主题的每条等宽栈都带 `"QQM CJK"`（等宽元素里也有中文） |
> | 卡片上残留 emoji（`⚠️` `🎬` `🔥`） | emoji **不在**任何 CJK 字体里，裸机上是方框或空白 | 卡片里不留 emoji：图标走矢量 `.ic-*`（纯 SVG 遮罩，零字体依赖）；纯文本兜底改用 `● ○ 注意：` 这种一定画得出来的字 |
>
> `test.mjs` 里钉着这一节（「自带字体覆盖」）。判据不是"猜 emoji 码位"，而是**复算**
> `scripts/build-fonts.py` 的覆盖集（声明的 unicode 区间 ∪ GBK 全集）—— 卡片模板 / 卡数据里
> 出现清单外的字就报红，并指名道姓给出文件与码位。加主题也要守这条：
> **引 `qqm-cjk.css`，并给等宽栈补 CJK**（内置主题的 mono 栈可以照 `nebula/_base.css` 的 `--mono` 抄）。

先看日志：每个进程第一次出卡时会打一行

```
[qqmusic-plugin] 卡片字体：命中 MiSans（本机可用：…）
```

* 命中 `MiSans` / `PingFang SC` / `HarmonyOS Sans SC` → 用的就是设计的那套，没问题；
* 命中别家（如 `Noto Sans SC`、`Microsoft YaHei`）→ 能用，但观感与设计稿有差；
* 打出 **警告**「字体栈里一个都没装」→ 就是这一节要解决的情况。

装字体（装完重启机器人即可，**不用**改任何配置）：

```bash
# Debian / Ubuntu 容器
apt-get update && apt-get install -y fonts-noto-cjk fonts-wqy-microhei fonts-noto-color-emoji
# RHEL / CentOS / Rocky
dnf install -y google-noto-sans-cjk-fonts google-noto-emoji-color-fonts
```

**卡片不再需要 emoji 字体**（这两行以前写着"emoji 也要装"，已作废）：会员锁 / 链接勾这类符号
都是 `.ic-*` 矢量图标（CSS 遮罩画 SVG，颜色跟 `currentColor` 走、尺寸跟字号走，不依赖任何
字体或网络资源），"有 MV" 是文字小标 `MV` —— 所以上面两条命令里的 emoji 字体装不装都行。
**聊天里**那批 emoji（帮助文本、纯文本兜底）由 QQ 客户端渲染，跟宿主字体无关，不受影响。

> 想更贴近设计稿可以装 **MiSans**（小米开源，可商用）：把 `MiSans-Regular/Demibold` 丢进
> `/usr/share/fonts/` 后 `fc-cache -fv`。**注意**：只装 Regular 一个字重时，卡片上的粗体
> 只能由浏览器"撑"出来，小字号中文会出现笔画糊连（这正是"字体残缺"最常见的成因）——
> 所以至少要装 Regular + 一个粗体。

## 适配器支持

| 能力 | OneBot 11（NapCat / Lagrange / LLOneBot） | QQBot 官方 | ICQQ 适配器 |
|------|:-----------------------------------------:|:----------:|:-----------:|
| 文本 / 图片 | ✅ | ✅ | ✅ |
| 语音 | ✅ | ✅ | ✅ |
| 视频（MV） | ✅ 直链 / 本地 | ✅ 直链 | ✅ 本地下载后发 |
| 群文件 | ✅ | ✅ | ✅ |
| 原生音乐卡 | 视协议 | — | 视协议 |
| 一起听（群听歌） | ✅ NapCat / SnowLuma（待实测） | — | ✅ |

> 📌 **关于原生音乐卡**：NTQQ 系协议端（NapCat / Lagrange / LLOneBot 等）不支持 go-cq 风格的 `type:qq` 音乐卡（该类型需协议端服务端拉歌单，会以 `retcode 1200` 拒绝）。插件在 OneBot 上**直接用 custom 卡**（带真实播放链 + 封面 + 歌手，效果与官方客户端分享一致，参考小飞插件做法）；ICQQ 适配器仍走原生 `type:qq`。同一适配器连续失败 3 次后本会话内自动跳过并静默降级为语音 / 群文件（点歌功能不受影响）。彻底关闭可在配置中关掉「发送原生 QQ 音乐卡」。
>
> 📌 **关于高音质语音**：FLAC 等高音质文件体积大，直接作为语音（record）发送会被协议端以体积/格式限制拒绝。插件发送语音前会自动用 ffmpeg 压成紧凑 mp3（保证能发出去），**群文件仍保留原始高音质文件**。需系统安装 `ffmpeg`（`ffmpeg -version` 可验证）。
>
> 📌 **关于群文件上传（OneBot/NTQQ）**：LLOneBot / NapCat / Lagrange 的 `upload_group_file` **动作**对 `.flac` 常报「未知文件类型或路径不存在」。插件 OneBot 上传优先用适配器原生 **`e.group.sendFile`**（与 rconsole-plugin 一致，能正常传无损 flac），失败才依次落到 `upload_group_file` → `send_group_msg` 文件段 → 压缩 mp3 兜底。ICQQ 走 `fs.upload`/`sendFile`。

> 📌 **关于一起听（群听歌）**：走 QQ 的 SSO 命令族 `QQAIOMediaSvc.*`（`share_trans` 入列 / `create_room` 开房），**不是**发一张 `com.tencent.together` 卡片 —— 那种卡只是「开始一起听」的邀请入口，客户端解析它时并不读卡片里的 token，复读或伪造它既开不出房间也排不进歌。
>
> **架构：协议知识全在 API 侧，插件只做「协议端识别 + 发送」。** 插件把群号/协议端/歌曲交给 API；API 算出「下一步该发什么包」并给出承载通道（`icqq` → `sendUni`，`onebot` → `send_packet`）；插件用自己的协议端会话把包发出去，再把响应原样交回 API，由 API 判定成败并给文案。插件里**不解析包、不做业务判断、没有字段定义**，所以它单独分出去也复刻不了这个功能。
>
> 支持的协议端：**ICQQ**，以及带 `send_packet` 扩展动作的 **OneBot**（NapCat、SnowLuma）；LLOneBot / Lagrange 没有该动作，会在首次调用后明确提示并停用。`#qqm一起听 状态` 可随时查看房间当前曲目。
>
> **首次启用要探测一次**（房间参数 aio_type/media_type 是逆向出来的，必须实测）：
> - `#qqm一起听 探测` —— **只读**，扫三个候选值。需要一个"对照"：群里得先有一起听房间（手机开一个）才分辨得出哪个对；
> - `#qqm一起听 探测 写入` —— **主动开房**：拿候选值依次真的 `create_room`、再回读状态看房间有没有建起来，**不需要群里先有房间**。命中后**自动把参数写进 API 的 `data/together.json`**，不用手填；命中即停（不会连开一堆房间）。
>
> 注意：写入模式会在群里留下真实房间（可能残留空房间，需要手动结束），**请在测试群跑**。
>
> **默认关闭**：Karin WebUI「启用一起听」`togetherEnable` 关着时指令不走 API（`#qqm一起听 探测` 除外，它是排障路径）；「点歌后自动同步」`togetherAuto` 是第二个开关，**要与总开关同时打开**才生效。
>
> 首次使用还要在真实群里探测一次：`POST /together/start {"action":"probe"}`（只读），把结果的 `aio_type`/`media_type` 写进 API 的 `data/together.json`（`aioType` 为 0 时同样拒绝写入）。探测不受开关限制。

> 📌 **关于卡片界面（多套 UI）**：所有图片卡片都由 `resources/themes/<主题>/` 下的模板渲染，**丢一个目录进来就是一套新 UI**（详见 [resources/themes/README.md](resources/themes/README.md)）。内置四套：`classic`（原始界面，1.x 默认）、`apple`（排印对齐 apple.com.cn 的实测值：近白底 + 白玻璃卡 + 蓝色小标），以及 **2.0 专版**的 `nebula`「星云 · 鎏光」（暖象牙底 + 液态玻璃 + 香槟金烫字，2.0 的默认主题）与 `multi`「多平台」（冷中性底 + 单一主光，来源色标走色轨/色点/同色玻璃标，一眼看出这首歌来自哪家）。四套都支持深色与时段配色。主人发 `#qqm界面` 查看与切换，深浅色支持「浅色 / 深色 / 跟随时间（夜晚自动深色）」，Karin WebUI 里都有。
>
> **换主题、改模板、改 `theme.json` 都是热更新** —— 不用重启机器人（渲染前比对文件 mtime，变了就让 art-template 重新编译；它默认按文件名永久缓存，这正是以前改模板必须重启的原因）。批量改动后想强制重来：`#qqm界面 重载`。
>
> 📌 **自定义背景（apple / nebula / multi 三套支持，classic 忽略）**：`#qqm界面 背景 <路径或链接>`（Karin WebUI 里也能设）。三种来源**自动识别**：服务器本地路径（`D:\图片\a.jpg` / `/root/pics/a.jpg`）、图片直链、图片 API（返回 JSON 里有图片地址，或直接返回图片）。开启后卡片材质自动切成 **iOS 液态玻璃**（半透明 + 强模糊 + 边缘高光）；2.0 的星云/多平台本来就是玻璃材质，背景图直接当"玻璃后面的那张墙纸"。
> 远端图**由插件侧取回并缓存成本地文件**（不让浏览器去拉）—— 否则每次渲染都要等远端图，慢图/挂掉的图会把整张卡拖死；缓存时长 Karin WebUI 可调（`0` = 每次渲染都换）。取不到图时**自动回落主题自带底色**，不影响发卡（日志里有原因）。
>
> 主题可以只实现部分卡片，缺的自动回落到 `classic`（**内置的四套必须实现全** —— 缺一张就会出现"内容是这套主题的、皮肤是经典绿"的拼接感，`test.mjs` 会拦）。本地预览（不进机器人）：`node scripts/preview-cards.mjs`，产出 `temp/preview/<主题>[-dark]/<卡>.png`，走的与生产同一条渲染路径。

> ⚡ **卡片图片格式：默认 JPEG（2026-09-25 性能优化）**：同一张 2.0 帮助卡（2064×6030）实测
> **PNG 4.98 s / 9.75 MB** → **JPEG(q92) 0.56 s / 1.44 MB**（快 8.9×、小 6.8×），1:1 局部对比看不出差别。
> 卡片每次都要上传给 QQ，慢网下"半天发不出去"多半就是这 8MB。Karin WebUI →「② 界面与外观 → 卡片图片格式」
> 可切回 `png`（做素材/海报时用）。二维码那条路**永远是 PNG**（JPEG 的振铃会让码扫不出来），
> 本地预览脚本也固定 PNG。

> ⚡ **帮助图是缓存的（2026-09-30，2C2G 专项）**：`#qqm帮助` 出的那张图**只跟"身份 + 配置 + 模板"有关**
> —— 十分钟内谁再发一次都是**秒回**（实测 2654ms → 1ms），换了主题 / 改了 Karin WebUI 开关 / 改了模板立刻重截。
> 弱机器（2C2G、无 GPU 的容器）上原来"每发一次都要等几秒"有两个原因：1.x 老帮助卡**根本没缓存**，
> 而且截图里有两段固定 `setTimeout` 白等。现在两条都修了；长卡还会按**像素预算**自动降清晰度倍数
> （8.7M 像素 → 截图 539ms、882KB），细节见「⚡ 性能红线」⑥⑦。

## Karin WebUI 配置

### 本地曲库优先

「本地曲库优先」默认开启。点歌结果会先列本地命中，同时保留 QQ 官方结果和已启用的第三方填充渠道；卡片与文本都会显示实际渠道。关闭后，搜索、播放链和外部链接解析统一传 `local=0`。在意本地文件音质时，还可以关闭「音质自动降级」。详见 [本地曲库与渠道显示](local-library.md)。

在 Karin WebUI 的插件配置页可直接修改：

> 配置项按**三大组**折叠（① 基础设置 / ② 界面与外观 / ③ 发送与下载）：字段与键名一个都没变，只是不用在一页里翻半天了。
> 组件树按 Karin 1.18 标准使用 `accordion -> accordion-item -> children`；保存时插件会把 WebUI 的分组数组展开并映射回 `platforms.<平台>.<字段>`，不会把点号字段名直接交给 React Hook Form。

- API 地址 / Token
- 插件、点歌、解析、扫码登录命令开关
- 点歌结果图片卡片开关（关闭回退纯文本）
- 最高音质 / 自动降级
- 语音 / 群文件 / 音乐卡 / 文本信息发送开关
- 禁用高清语音（PC QQ 播放不了高清语音时开启，语音改发 mono16k 低音质）
- 点歌列表数量 / 下载超时 / 文件保留时间
- 试听片段秒数（默认 30）/ 订阅扫描间隔（默认 6 小时）/ 每群订阅与定时上限
- 接管无前缀「#点歌」（默认关；开启后不加 `#qqm` 前缀的点歌也由本插件处理）
- 其它平台补充曲（默认开；QQ 音乐没有的免费曲从网易云/酷我补进来，128k）
- 音源平台：一家一个页签，各自独立的开关 / 点歌条数 / **凭据段**（能扫码的给扫码命令说明，能粘贴的给 cookie 输入框 —— 凭据只上传到 API，不写进插件配置）
- 一律走主人账号（默认开；主人账号自动取最近扫码登录的账号，所有人点歌都按主人的 ck，Karin WebUI 可关）
- 主人账号手动指定（`publicAccount`，留空=自动；多账号想固定用某一个时才填）
- 从 API 一键回填登录态
- 一起听：启用开关（默认关）/ 点歌后自动同步（默认关，需总开关同时打开）—— 协议参数在 API 侧：`data/together.json` 的 `aioType`/`mediaType`/`shareAppid`/`cutSong`/`autoCreate`
- 听歌时长统计（默认开）：`#qqm听歌` / `#qqm听歌榜` 的数据源 —— 保留天数（默认 60）、每群人数上限（默认 100）；纯本地账本，不碰平台账号
- 勋章进度（默认开）：`#qqm勋章` 的数据源 —— 按请求者本人账号只读查**平台侧**的听歌时长与勋章任务进度（上游可能拒绝本次查询）；`medalActID` 留空时以播放页任务兜底
- 界面：卡片主题（`resources/themes/` 下的目录名，内置 classic / apple / nebula / multi；2.0 打开后走 `uiThemeV2`，默认 nebula）、深浅色（浅色 / 深色 / 跟随时间）、底色跟随时段、自定义背景（开关 + 来源 + 缓存分钟数，仅 apple 主题支持）

## ⚡ 性能红线（改代码前先看）

卡片是高频操作，而插件与所有别的插件共用**同一条事件循环** —— 下面几条都是踩过之后写下来的：

**① 判定必须每次现读配置，别缓存在模块顶层。**
`#qqm界面`、「？？？」开关这类判定（`utils/v2.ts`）每次都拿 `Config.getConfig()` 现算。老代码把开关读一次写进模块变量，Karin WebUI 里改完要重启才生效，而且「未开启」那个分支还会被缓存成永久的。

**② `Config.getConfig()` 的结果按文件指纹（mtime + size）缓存，返回深层副本。**
一次调用要读 + 解析**两份** yaml（实测 ~4.2ms，而且是同步的），一条命令里会被叫好几次，所以必须有缓存；但缓存的是**文件内容**、不是判定结果 —— Karin WebUI 保存 / 手改 yaml / 插件更新覆盖 `default_config`，指纹一变下一次就立刻读到新的（`setConfig` 另有一次主动失效）。返回值是深层副本，调用方改嵌套对象也不会污染缓存。

**③ 卡片模块只能动态 import。**
`utils/card-data.ts` / `utils/render.ts` 会把 art-template 和 Puppeteer 一起拉起来，不能在插件启动时加载（列表卡的统一出口 `replyListCardOrText()` 就负责这件事）。

**④ 渲染共用同一个 Chromium，且别把 `waitUntil` 改回 `networkidle0`。**
以前每张卡都 launch + close 一次 Chrome（实测 launch 545~1368ms、close 232~256ms），而截图本身才 ~600ms —— 一半时间白烧。现在 `utils/render.ts` 是**单例浏览器**（空闲 5 分钟自动关、进程退出时 kill），每张卡只开 / 关一个 page。
`waitUntil` 必须留在 `'load'`：内置 44 张模板**一个 `<script>` 都没有**，也没有远程字体；`networkidle0` 在 `file://` 上要等满 500ms 静默窗口（实测 goto 975ms → 65ms），后面仍然显式等 `document.fonts.ready`，不会丢字。
落定**不许再写固定 `setTimeout`**：老代码是 `setTimeout(200)`（重设视口后再 80ms），实测 22 张真卡片双 rAF 与它截图**字节完全一致**，却白等 130~230ms/张，而慢机器上 200ms 又赌不赢一帧。现在统一走 `waitFrames()`（等两帧，带 1s 兜底防后台标签页不派发 rAF）。

**⑤ 列表卡别各写各的。**
排行 / 新歌 / 歌手 / 专辑 / 歌单 / 点歌的「动态 import + 渲染 → 文本兜底」统一走 `utils/common.ts` 的 `replyListCardOrText()`；热搜卡与评论卡**不是**列表卡，别顺手收进去。

**⑥ 帮助图（1.x 老卡与 2.0 新卡）都要走缓存，别每次现截。**
`renderHelpCard()` / `renderGuideCard()` 都过 `renderHelpCardCached()`：帮助卡内容只跟「身份 + 配置 + 模板」有关，键一样就直接把上一张图还回去 —— 实测 **2654ms → 1ms**（1.x）、**1473ms → 1ms**（2.0）。1.x 老帮助卡（默认配置走的那张，592×3654 CSS、8.7M 像素）以前**根本没有缓存**，所以默认环境下"每发一次 #qqm帮助 都要等好几秒"。
⚠️ 键里必须带**模板 mtime**（`templateStamp()`）：`#qqm更新` 换了模板而进程没重启时，光看配置是发现不了的 —— 少这一项就会发出旧模板截的图。缓存有上限（`HELP_CACHE_MAX`），改 Karin WebUI 会换键，别让它无限长。

**⑦ 长卡按像素预算降 dpr（`deviceScaleFor()`）。**
像素数直接决定光栅 + JPEG 编码的耗时，而 2C2G / 无 GPU 的容器走软件光栅，这一步最贵。本机 `--disable-gpu` 实测 2.0 帮助卡：dpr3 = 12.9M 像素 / 截图 1124ms / 1082KB；**dpr2 = 5.7M 像素 / 484ms / 606KB**；1.x 帮助卡 dpr3 = 19.5M / 962ms → dpr2 = 8.7M / 539ms。预算 8M，超了降 2 倍、不超保持 3 倍（小字更锐）；量不到尺寸时保持老行为（3 倍），别猜。

实测收益：同一张状态卡（`multi` 主题）热态渲染 **3322ms → 1654ms**（约 -50%）；`Config.getConfig()` 命中缓存 **4.22ms → 0.107ms**（约 39×）；帮助图命中缓存 **~2s → 1ms**。`test.mjs` 的「2.0 重构收口」段把这些不变量钉成了断言。
